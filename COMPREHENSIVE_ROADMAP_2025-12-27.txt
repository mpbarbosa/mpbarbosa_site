10. DEPLOYMENT ARCHITECTURE
═══════════════════════════════════════════════════════════════════════════════

TWO-STEP DEPLOYMENT (v3.0.0):

STEP 1: STAGING (Git-based)
├─ Source: mpbarbosa_site/src/ + 4 sibling projects
├─ Target: ../mpbarbosa.com/ (staging repository)
├─ Features: Full version control, validation, rollback capability
└─ Command: ./shell_scripts/sync_to_staging.sh --step1

STEP 2: PRODUCTION (nginx server)
├─ Source: ../mpbarbosa.com/
├─ Target: /var/www/html (production server)
├─ Features: Automatic backups, rollback via git history
└─ Command: sudo ./shell_scripts/deploy_to_webserver.sh

SIBLING PROJECT PATHS (Clean Architecture - No submodules/):
├─ Music in Numbers: public/music_in_numbers/ (Client-side)
├─ Guia Turístico: public/guia_turistico/ (Client-side)
├─ Monitora Vagas: public/monitora_vagas/ (Client-side)
└─ Busca Vagas: public/busca_vagas/ (Backend API)

ADVANTAGES:
✅ No git submodules (independent sibling architecture)
✅ Full version control in staging repository
✅ Each project updatable independently
✅ Scalable for new projects
✅ Clean deployment paths (legacy submodules/ removed)
